# Writing a plugin without the Rust SDK

A plugin is a WASM component, so any language with a component toolchain can in principle produce one. The Rust SDK
(`hestia-sdk`) is the only path that is built, tested and supported. Nothing in this repository or in
[prytaneum/plugin-examples](https://github.com/prytaneum/plugin-examples) builds a plugin in another language, so
**every other language below is untested**. This page says what the contract is and what the toolchains currently
document; verify each step yourself.

## The contract

The ABI is one WIT package, `hestia:plugin@1.0.0`, in [`crates/sdk/wit/`](../../crates/sdk/wit) (licensed
`MIT OR Apache-2.0`). Its version is the plugin API version, and the manifest's `api = "^1.0.0"` is a caret requirement
on it ([0091](../decisions/0091-plugins-are-wasm-components.md)).

`plugin.wit` defines the world your component implements:

```wit
world plugin {
    import log;
    import host;
    import process;
    import progress;
    import settings;
    import ipc;
    export lifecycle;
    export commands;
    export events;
    export settings-changed;
    export ui;
    export hooks;
    export provider;
}
```

- The host imports the guest gets: `log`, `host` (`call` and `run-job`, which reach daemon channels), `process`,
  `progress`, `settings` and `ipc`.
- The exports are fixed too: `lifecycle.init`, `commands`, `events`, `settings-changed`, `ui` (`render`, `action`),
  `hooks` and `provider.invoke`. Hook points, provider kinds and event topics are data in `proto`, not new exports
  ([0106](../decisions/0106-the-plugin-api-is-mechanisms-not-features.md)).
- Payloads are JSON strings (`type json = string`), shaped like the matching `proto` types. Errors are the
  `plugin-error` variant: `permission-denied`, `not-found`, `invalid`, `failed`, `unsupported`.
- `deps/` holds the WASI 0.2.12 packages the world builds on (`wasi:cli`, `clocks`, `filesystem`, `http`, `io`, `random`,
  `sockets`). The Rust SDK imports `wasi:http` through a separate world, `http-client`, so a guest that never touches the
  network does not carry it.
- The host runs components on wasmtime with WASI 0.2. WASI 0.3 is not targeted
  ([0091](../decisions/0091-plugins-are-wasm-components.md)). A toolchain that defaults to 0.3 must be pointed at 0.2.

## Calling the host without Rust

In Rust, `hestia::call::<C>` takes the contract's typed params and result. Outside Rust, `host.call(channel, payload)`
takes a channel name and a JSON string, and returns a JSON string. Nothing checks either side at compile time, so the
shapes come from the generated TypeScript in [`frontend/src/api/types/`](../../frontend/src/api/types):

- `channels.ts` maps every channel to its params and result, every job channel to its progress and done payloads, and
  every topic to its event payload. The individual types are in `generated/`. All fields are `camelCase`.
- Only channels that name a permission on their contract are open to a plugin; the rest are closed to plugins
  ([permissions.md](permissions.md)). `channels.ts` lists all channels, plugin-reachable or not.
- Provider operations use the types in `frontend/src/api/types/generated/` too (`SearchQuery`, `JavaBuild`, `FormatCopy`
  and so on; see [providers.md](providers.md)), and page trees use `UiNode` and `Effect` ([ui.md](ui.md)).
- The TypeScript is generated by `scripts/gen-types.sh` and is the only typed description of the JSON outside Rust.

## Building and installing

The command-line workflow assumes Rust: `hestia plugin pack` runs `cargo build --release --target wasm32-wasip2` for a
plugin with a component, and writes `api` into the manifest from the `hestia-sdk` version cargo resolved. A plugin that
is not a cargo crate cannot be packed that way. What does work, from the code:

- Write `plugin.toml` yourself, with `wasm = "plugin.wasm"` and `api = "^1.0.0"`. A manifest with a component and no
  `api` is refused ([manifest.md](manifest.md)).
- Put `plugin.toml` and the component in a folder (with `assets/` and `themes/` if you have them) and run
  `hestia plugin add <folder>`. A folder is installed as an unpacked package, and the permissions it asks for are shown
  for approval like any other.
- A hand-made `.hplugin` is a zip of the same files. Publishing through `hestia plugin index` and the workflows in
  [publishing.md](publishing.md) reads cargo metadata, so a non-Rust plugin has no tested route into a repository.

Whatever the language, the result must be a component, not a core module, whose imports the world above and WASI 0.2
satisfy.

## JavaScript and TypeScript

Status: untested here.

Toolchain: `jco` with `componentize-js` (Bytecode Alliance).

```bash
npm install -g @bytecodealliance/jco
jco componentize --wit crates/sdk/wit --world-name plugin --out plugin.wasm plugin.js
```

- The component-model book installs `jco` globally with `npm install -g @bytecodealliance/jco` and notes that it uses
  `componentize-js` internally; both can instead be installed per project with `npm install -D`.
- Its build example passes `--wit`, `--world-name` and `--out` and a source file. The `--wit` path here is this
  repository's `crates/sdk/wit` directory, which also contains the `deps/` the world needs. The same example passes
  `--disable=all` to remove WASI access, which would also remove `console.log`, `Math.random` and clocks; a plugin
  using the `hestia:plugin/log` import does not need `console`.
- The jco README says its bundled starting points default to WASI 0.3, and `@0.2.x` selects WASI 0.2. Target 0.2.
- The README also notes that on Node 18 with `componentize-js` 0.18.3 or later you may need to install `oxc-parser`
  manually, and that npm older than 11.3.0 can have trouble with optional dependencies.
- Types for `host.call` payloads come straight from `frontend/src/api/types/`: copy or import them.

The command above is assembled from the documented example, not run against this WIT.

## Go

Status: untested here.

Two toolchains exist, and their guidance has changed, so check the current one:

- The component-model book's Go page now uses **componentize-go**, a Bytecode Alliance tool that needs a recent Go (the
  book states Go 1.25.5 or later; the repository README states a newer minimum for installing through Go). Its
  example is `componentize-go --world <world> bindings`, then `go mod tidy`, then `componentize-go build`.
- **TinyGo** has had a `-target=wasip2` since v0.34, with `wit-bindgen-go` generating bindings. A community guide
  recommends v0.39 or later, and one report says TinyGo defaulted to the `wasi:cli/command` world instead of a custom
  one, citing an upstream fix that the sources do not confirm shipped. The wasip2 target assumes the `wasi:cli` imports are
  in the world.

Neither is verified against `hestia:plugin`. Before committing to Go, build a component that exports only `lifecycle`
and check that `hestia plugin add <folder>` loads it.

## Python

Status: untested here.

Toolchain: `componentize-py` (Bytecode Alliance). Python 3.10 or later.

```bash
pip install componentize-py
componentize-py --wit-path crates/sdk/wit --world plugin componentize app -o plugin.wasm
```

- The book's example is `componentize-py --wit-path wit/component.wit --world adder componentize app -o add.wasm`, with
  `app` the Python module; `bindings` is optional, for editor support, and fails if its output folder already exists.
- The repository README lists a limitation: dependencies can only be imported at build time, at the top level of the
  module.
- The book notes that a host must add WASI to its linker for components that use it. Hestia's host runs WASI 0.2
  ([0091](../decisions/0091-plugins-are-wasm-components.md)).

The command is assembled from the documented example, not run against this WIT.
